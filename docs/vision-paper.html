Vision Paper · Arbeitsstand

devfront.dev

Ein Anno-/Sandbox-City-Builder für echte Dev-Arbeit: Missionen, Skills, Guilds und sichtbarer Fortschritt — gebaut als Open-Source-Vertrauensanker.

Nicht „Jira mit XP“. Nicht „Coding-Lernspiel“. Nicht „Play-to-earn“. Die Kernfantasie: Du baust keine Fantasie-Stadt durch Klicks, sondern eine technische Welt durch echte Arbeit.

Real work → visible progress → better missions → stronger base.
MVP: persönliche Base/Kolonie Später: Welten, Planeten, Universen GitHub-verifiziert + private Missionen Open-source entwickelt

1. Kernthese

devfront macht produktive Entwicklungsarbeit emotional sichtbar. Der wichtigste Reward ist nicht Status, Geld oder ein Badge, sondern das Gefühl: Meine echte Arbeit baut etwas Sichtbares auf.

Primärer Reward

Die eigene Base/Welt wächst sichtbar. Das ist das Herz des Produkts.

Stützende Rewards

Skillentwicklung und Guild-/Team-Aufbau geben Tiefe und langfristige Motivation.

Nebenprodukte

Mission Discovery ist Utility. Reputation und Status entstehen nebenbei durch echte, verifizierte Arbeit.

4. Arbeits-Input

devfront darf nicht nur Open Source abbilden. Gleichzeitig braucht es Vertrauenssignale. Darum gilt: GitHub-verifizierte Arbeit ist Goldstandard, private Missionen bleiben möglich.

Gold Progress

PR merged, Issue closed, Review approved, Tests passed, Deployment, CI-Signale. Öffentlich/verifiziert und stärker gewichtet.

Private Progress

Manuelle Missionen für Kundenarbeit, internes Projekt, Lernaufgabe oder Agent-Workflow. Zählt für die Base, aber anders markiert.

Guided Progress

Empfohlene Missionen auf Basis von Skills, Stack, Zielen, Base-Ausbau und optionaler GitHub-Historie.

5. Mission-System

Eine MVP-Mission ist eine echte 1–4h-Arbeitseinheit. Größere Arbeit wird später als Campaign aus mehreren Missionen dargestellt.

TypUmfangBeispieleReward-Prinzip
Small Mission15–60 MinutenDocs-Fix, Bug reproduzieren, Issue triagierenKleine XP/Ressourcen, schneller Momentum-Gewinn
Standard Mission1–4 StundenBugfix, Test ergänzen, kleiner Feature-Slice, UI-AnpassungMVP-Standard: echter Fortschritt ohne Overhead
Major Mission0.5–2 TageIntegration, Modul-Refactor, größeres FeatureMehr XP, stärkere Verifikation, höherer Impact
CampaignMehrere Missionen„Checkout stabilisieren“, „AI Review Pipeline bauen“Zusätzlicher Abschlussbonus und sichtbarer Weltfortschritt

Reward-Formel als Designregel: XP/Ressourcen entstehen aus Umfang × Schwierigkeit × Wichtigkeit × Verifikation × Qualität × Impact — nicht nur aus Zeit.

6. Basebuilding-System

Jede abgeschlossene Mission erzeugt drei Dinge: Skill XP + Ressourcen + sichtbaren Fortschritt an Base/Gebäude.

Build

Code, Features, Implementation, UI, Produktarbeit. Gebäude: Workshop / Forge / Construction Yard.

Stability

Tests, Bugfixes, QA, Security, Reliability. Gebäude: Shield / QA Tower / Defense Grid.

Knowledge

Docs, Research, Architektur, Entscheidungen, Tutorials. Gebäude: Archive / Library / Observatory.

Trust

Reviews, Mentoring, Zusammenarbeit, Kommunikation, verifizierte Beiträge. Gebäude: Signal Tower / Embassy / Guild Hall.

Automation

AI-Workflows, DevOps, CI/CD, Agents, Tooling. Gebäude: Automation Lab / Engine Core / Drone Bay.

Beispiel

„Test für Login-Flow schreiben“ → +Testing XP, +Stability, +Trust, Shield-Gebäude wächst sichtbar.

9. Open Source als Akzeptanzanker

Das Spiel/die Plattform selbst sollte open-source entwickelt werden, damit Entwickler vertrauen, mitgestalten und die Mechaniken akzeptieren. Open Source ist aber nur eine von vielen möglichen Welten.

Warum open-source?

  • Vertrauen bei Entwicklern
  • Keine Blackbox bei Skill-/Reputationslogik
  • Community kann eigene Welten/Integrationen bauen
  • Glaubwürdiger Start in Dev-Communities

Warum nicht nur Open Source?

  • Dev-Arbeit passiert auch privat, intern und kommerziell
  • Guilds und Teams brauchen geschützte Räume
  • Spätere Firmenwelten, Sponsoring und Recruiting bleiben möglich
  • Produkt wird größer als GoodFirstIssue/CodeTriage
