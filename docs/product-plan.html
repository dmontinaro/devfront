Product and MVP Plan · August 17, 2026

Real work shapes a visible world.

devfront turns software development with humans and agents into missions, skills, resources, and visible world transformation. The core is not decorative gamification, but a playable progression layer powered by real work.

North Star
Every completed mission must visibly change the player’s world.

If that moment is not motivating, guilds, universes, and monetization will not save the product.

Working definition
World Builder × GitHub × Agentic Work

A persistent world-building layer for real work. Not an RPG and not a ticket tracker with points.

Executive summary

What we are actually building

The first release is a focused personal world-builder powered by real development work. Players choose a world goal, complete a mission, and receive skill XP, resources, and a visible transformation.

01 / GAME FANTASY

Shape a living technical world

The world is home, progress record, and emotional reward. Projects and capabilities become visible regions, systems, landmarks, and relationships.

02 / REAL INPUT

Real work instead of fake quests

GitHub signals provide verified Gold Progress. Private and manual missions remain possible and carry transparent evidence markers.

03 / PRODUCT WEDGE

Personal loop first, connected worlds later

The MVP must prove motivation and return behavior. Public repositories, guilds, company worlds, and strategy build on that loop.

Recommendation

Build a 2D world-building vertical slice first.

One starting world, five domains, three real missions, and one strong transformation moment are enough to test the core hypothesis.

Why: 3D, universes, and multiplayer would consume months before we know whether visible world progress makes real work more motivating. The first prototype only needs to make this path compelling: Choose mission → complete work → understand reward → see the world transform

MVP Boundary

A scope that produces a real answer

The MVP is not a minimal data model. It is a minimal emotional proof: expressive enough to make transformation rewarding, but small enough to test quickly.

In Scope

  • Self-selection onboarding: role, stack, and goal
  • Personal 2D starting world with five domains
  • Manual missions plus selected GitHub missions
  • Missions as real work units of roughly one to four hours
  • Skill XP, five resources, and visible transformations
  • One high-quality completion and transformation moment
  • Player profile with skills and completed missions

Intentionally excluded from the MVP

  • Open universe and freely explorable star systems
  • Guild worlds, PvP, attacks, or complex strategy
  • Company missions, bounties, and recruiting
  • 3D world, free camera, and elaborate avatars
  • Global leaderboards, tokens, or play-to-earn
  • Fully automated quality and impact scoring
  • A replacement for GitHub Issues or project management

Roadmap

From proof to universe

Each phase has an evidence gate. The next stage begins only when the previous one answers a real product question.

Phase 0 · Now

Playable UX Prototype

World home, mission card, completion flow, and transformation moment as a clickable HTML prototype.

Gate: the loop is understandable without explanation and emotionally compelling.
Phase 1 · MVP

Personal World Loop

Onboarding, missions, resources, five world domains, profile, and local progress.

Gate: testers voluntarily return for more missions.
Phase 2 · Trust

GitHub Gold Progress

Login, issue/PR/review signals, verified completion, and traceable evidence.

Gate: verification increases trust without burdening the flow.
Phase 3 · World

Open Source World

Public repository worlds, curated mission board, community loop, and first shared goals.

Gate: repositories gain useful contributions rather than additional review burden.
Phase 4 · Network

Guilds, private worlds, and universe layer

Shared worlds, private project worlds, connected universes, and later strategic interaction.

Gate: social systems amplify productivity rather than distraction.

Risks

What can break the concept

The largest risks are not technical. They are bad incentives, weak emotional quality, and premature scope expansion.

High

The reward feels cosmetic

If the world is only numbers with different graphics, the fantasy fails. Transformations need visible form, function, and meaning.

High

XP farming displaces good work

Merge, review, quality, and impact must matter more than raw activity or time.

Med

Agent work is difficult to attribute

Evaluate accountable output, not prompt count or automatically generated commits.

Med

Game and tool become disconnected

Missions must connect directly to world goals. Otherwise the world becomes a dashboard beside the real work.

Next steps

The next three moves

Do not expand the concept further yet. The next insight comes from a playable, visually compelling core loop.

NOW · M

Playable World Prototype

Build an interactive 2D prototype with a starting world, one transformation goal, three missions, and a reward sequence.

Outcome: testable HTML vertical slice
NEXT · S

Run five users through the loop

Observe whether they understand the goal, choose a mission, and feel motivated by the transformation.

Outcome: qualitative loop validation
LATER · M

Define the MVP domain model

Model mission, work evidence, reward, resource, skill, world element, and transformation based on the test.

Outcome: implementation-ready MVP scope
